# Resend webhook ingestion into lead conversation history, with forward-only lead status

Outreach sends now append an outbound message to `marketing_outreach_leads.conversation_history` and tag the Resend email with `toolbit_source=outreach_lead` + `lead_id`. A new svix-signed webhook at `/api/webhooks/resend` applies delivery events to the stored message. It also fetches replies from `GET /emails/receiving/:id?html_format=cid` and stores them in the matching thread. All writes go through `service_role`-only Postgres functions, which also perform the automatic `pending → emailed → replied` promotion. The migration was applied to a scratch Postgres (PGlite 0.5.8 with a replica of the live table, its trigger and its constraints). The outbound and status-automation scenarios there behave as specified. The problems found are all on the inbound path.

Watch for:
- The HTML→text fallback runs on uncapped, sender-controlled HTML and is quadratic (confirmed: 200 KB takes 13.6 s).
- Inbound bodies that contain NUL, or are truncated in the middle of an emoji, are rejected by `jsonb` and answered 500 on every retry (confirmed).
- Inbound de-duplication only checks the chosen lead. A retried reply from an address shared by several leads can be stored on two leads and promote both (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

On the scratch replica, all of these pass:
- The first `delivered` promotes the lead to `emailed` and records `metadata.status_automation`.
- A replayed event after a manual change is ignored.
- A BCC-recipient event only back-fills the Message-ID.
- `launched` and custom statuses are left alone.
- Duplicate and auto-reply ingests don't promote.
- anon and authenticated get `permission denied` on every write RPC.

The weak spot is inbound matching. Idempotency is checked only within the chosen lead. The thread-email and business-email paths choose among candidate leads by `updated_at`, and every status edit or delivery event changes that.

Apart from the signature check and the 503 "not recorded yet" window, every failure in the webhook becomes a 500. That includes deterministic ones. A payload Postgres will never accept is retried through Resend's whole schedule and then dropped.

For HTML-only replies, ingestion converts HTML to text with regexes that backtrack quadratically, and it does this before any size cap. After that, `capText` truncates with `slice`, which can split a surrogate pair. NUL characters pass through untouched. Either case makes the ingest RPC fail.

Untrusted HTML is only rendered in `sandbox=""` iframes, but remote images and CSS in a reply still load when it's opened. The received-list action forwards raw Resend objects, unlike the details action. `marketing:view` is enough to read every inbound email on the Resend team, not only outreach replies.

Without the migration, the dashboard still works, including the leads list fallback. The webhook answers 500 to every event until the migration is applied, so apply it before creating the Resend endpoint.

### Quadratic HTML-to-text fallback on sender-controlled HTML

When a reply has no text part, `buildInboundMessage` calls `htmlToPlainText(email.html)` on the full HTML (conversation-store.ts:258). `capText` only runs after that. Two patterns in the chain backtrack quadratically. `/<[^>]+>/g` does it on a run of `<` with no `>`. `/<(style|script|head)[\s\S]*?<\/\1>/gi` does it on unclosed openers. Timing the same chain in Node:

```
 50 KB "<" run:   798 ms      50 KB "<style" run:  187 ms
100 KB "<" run:  3171 ms     100 KB "<style" run:  732 ms
200 KB "<" run: 13638 ms     200 KB "<style" run: 3170 ms
```

The cost grows 4× per doubling, so a 1 MB HTML-only message costs minutes of CPU per attempt. Any sender outside `MARKETING_OWN_EMAIL_DOMAINS` can trigger it. Each attempt outlives the webhook timeout, Resend retries on its schedule, and the reply is never stored. Capping alone isn't enough, since 200 KB already takes 13 s. These replacements run in linear time. 1 MB of either input finishes in under 5 ms, and normal HTML produces the same output:

```ts
const rawText = email.text || (email.html ? htmlToPlainText(email.html.slice(0, MAX_HTML_CHARS)) : '');

// in htmlToPlainText
.replace(/<(style|script|head)\b[\s\S]*?(?:<\/\1\s*>|$)/gi, '')
// ...
.replace(/<[^<>]*>/g, '')
```

### Payloads Postgres refuses, and the retry-forever path

`capText` truncates with `v.slice(0, max)` (conversation-store.ts:110). On a body longer than 50 K text or 200 K HTML chars, the cut can land between the two halves of a surrogate pair. `JSON.stringify` then emits a lone `\ud83d`, and `jsonb` rejects it with "invalid input syntax for type json". NUL characters in text or HTML fail the same way ("unsupported Unicode escape sequence"). Both failures were reproduced on the scratch Postgres. The RPC error is wrapped in `RetryableError`, the route answers 500, and Resend redelivers the same payload until its schedule runs out. The reply is never stored.

Outbound logging has the same exposure. `recordOutboundMessage` swallows the error, so the send is not recorded anywhere. Its delivery webhooks then get 503 for 10 minutes before giving up.

The other half of the problem is how failures are classified. Every Supabase error in `applyOutboundStatus` and `ingestReceivedEmail` becomes `RetryableError`, and the route returns 500 whether or not the error can succeed on retry. The retryable flag is only logged. Supabase errors carry `.code`. Postgres class `22xxx` and `P0001` (the functions' own `RAISE EXCEPTION`) fail the same way on every retry. Answering those with a logged 200 keeps poison events out of Resend's retry queue. Sanitizing at the source removes the most likely triggers:

```ts
const clean = (s: string) => s.replace(/\u0000/g, '').toWellFormed();
```

Apply it to body_text, body_html, subject, from and to.

### Inbound de-duplication and lead choice for shared addresses

`marketing_append_conversation_message` de-duplicates by `resend_email_id`/`message_id`, but only within the locked lead. `marketing_ingest_inbound_email` picks that lead first. It tries In-Reply-To, then leads where the sender already has a thread ordered by `updated_at DESC` (migration:551-558), then business emails, also ordered by `updated_at DESC` (:566-574).

The following sequence was reproduced on the scratch replica. Two leads have both emailed `shared@corp.ai`, and no Message-ID has been back-filled. The first `email.received` lands on lead B. A delivery event then touches lead A and bumps its `updated_at`. When Resend redelivers the same `email.received`, it is stored again, this time on lead A:

```
first delivery  -> processed, lead 5555… (thread_email), lead_status_changed: true
retry           -> processed, lead 4444… (thread_email), lead_status_changed: true
leads containing in1: Shared1 (replied), Shared2 (replied)
```

Live data has 10 business emails shared across leads; one is on 8 leads. The choice on first delivery is also arbitrary, because `updated_at` changes on any status edit or delivery webhook, not only on conversation activity.

Two changes address this. First, add a check across all leads at the top of the function, using the same GIN containment probe as `marketing_lookup_inbound_links`. Second, order the fallback paths by the thread's latest outbound timestamp. If two first deliveries can arrive concurrently, taking `pg_advisory_xact_lock(hashtext(v_resend_id))` before the check serializes them.

```sql
SELECT l.id INTO v_lead_id
  FROM public.marketing_outreach_leads l
 WHERE l.conversation_history @> jsonb_build_array(jsonb_build_object('messages',
         jsonb_build_array(jsonb_build_object('resend_email_id', v_resend_id))))
 LIMIT 1;
IF v_lead_id IS NOT NULL THEN
  RETURN jsonb_build_object('status', 'duplicate', 'lead_id', v_lead_id);
END IF;
```

### Status automation edge cases

The business-email path stores any email from a lead's listed address and promotes the lead, even if it was never emailed. On the replica, a `pending` lead with no outbound message became `replied` this way. Either require an outbound message on the thread, or skip promotion when `match_type = 'business_email'`, so that `replied` means "replied to outreach".

The second business-email probe, `business_emails @> ARRAY[btrim(p_from_email)]` (migration:572), can't match anything the first probe misses, because the TS caller lowercases the sender before calling. As a result, a stored `Team@Gamma.ai` comes back `unmatched` (reproduced). One live row has a mixed-case email.

`bounced` and `failed` share rank 3, and a status update applies when `new >= old` (migration:416). A later `email.failed`/`email.suppressed` overwrites a `bounced` and its error text, and vice versa (reproduced).

`conversation_summary` casts `(msg ->> 'is_auto_reply')::boolean` (migration:682). A value such as `"maybe"` raises "invalid input syntax for type boolean". The computed field is part of the list select, so one bad row breaks the leads list, and the fallback regex (`/conversation_summary/`) doesn't match that error. Today only our code writes this key, but RLS lets admins write the column directly. The ingest function already uses the safe form, `p_message -> 'is_auto_reply' = 'true'::jsonb`.

### Inbound HTML rendering and what reaches the browser

`sandbox=""` blocks scripts, forms, popups and navigation, but not subresource loads. Remote `<img>`, CSS `url()` and web fonts in a reply are fetched as soon as the HTML view renders. That view opens by default when the reply has no text part (`useState(!visible && hasHtml)`), so the sender learns when the reply was read and from which IP. Adding `<meta http-equiv="Content-Security-Policy" content="default-src 'none'; style-src 'unsafe-inline'; img-src data:">` to the generated document stops these loads, and a "load remote images" toggle could relax it on demand.

`<base target="_blank">` does nothing under `sandbox=""` because popups are blocked, so links in the HTML view don't work. Adding `allow-popups allow-popups-to-escape-sandbox` would make them clickable. That is safe as long as `allow-scripts` and `allow-same-origin` stay off.

`getResendReceivedEmailDetailsAction` picks fields explicitly ("never forward signed raw-download URLs"). `getResendReceivedEmailsAction` instead returns `{ ...item, link }` (actions.ts:1106), which forwards whatever the list endpoint returns now or adds later.

Both actions only require `marketing:view`, and they list and open every email received on the Resend team, not just linked outreach replies. `DEFAULT_BCC_EMAIL` is enabled on `toolbit.ai`. If that domain receives mail through Resend, this scope includes internal mail.

### Test coverage

There are no automated tests, and the project has no test runner. For this review, `tsc --noEmit` is clean. `eslint` on the in-scope files reports one error (OutreachLeadsTable.tsx:430, unescaped `'`). The migration and the scenarios above were run on the scratch PGlite replica. Not tested: the route with real svix-signed requests, and ingest against real Resend payloads.

Not verified, because it depends on Resend behavior that couldn't be checked offline:

- **Recipient in delivery events.** The BCC guard (resend-webhook.ts:126 → the migration's recipient filter) assumes `data.to` holds the individual recipient. Every outreach email currently has a BCC recipient.
- **`message_id` in `email.sent`/`email.delivered`.** In-Reply-To matching, and the reason given for the 503, both depend on it. Without it, every reply falls back to thread-email matching, which makes issue 5 more likely.
- **Shape of `headers` from `GET /emails/receiving/:id`.** `getHeader` iterates `Object.entries`. If Resend returns an array of `{name, value}`, In-Reply-To matching and header-based auto-reply detection would silently stop working.
